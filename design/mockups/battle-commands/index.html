Battle commands — individual buttons with their own tap response

Today one command is always highlighted in gold. That highlight is a keyboard cursor, drawn on a touch screen where it means nothing — so the screen looks like it has already chosen for you. These three variants remove the resting selection, give every button its own press response, and keep the gold cursor alive for arrow keys only. Tap the buttons. Every cell is live.

Simulate keyboard cursor: hidden (touch)

Real arrow keys and Enter work too. Arrows reveal and move the gold cursor across all three new variants at once; the next touch anywhere hides it again. The bottom-right cell ignores this — it is today's build.

For comparison What ships today. Same buttons, honest reproduction — a resting gold selection that never goes away, and no press response at all.

Notes

  • Where the numbers come from. design/GAME-FEEL.md token input.feedback = "under 80ms first response". Every press here starts at 0ms and completes its inward move in 60–70ms, inside that token. Release durations (90–100ms) come from the game-design skill's input-feedback band, 50–100ms ease-out. Nothing was invented for this feature.
  • One effect, not three. A tap is the most common event in the game, so the juice budget is tier‑1: one effect. A and B spend it on a scale punch, C spends it on a flash. None of them stack both, and none of them add shake, particles or hit-stop — that treatment is reserved for level-ups and boss kills, and spending it here would flatten those.
  • The keyboard is not sacrificed. The gold cursor is now gated on the last input device: arrows and Enter show it, the next touch hides it. Keyboard and gamepad play is unchanged; touch simply stops being shown a cursor it never asked for.
  • Response fires on press, confirm fires on release. That matches how the shipped overlay already routes battle taps (it commits on pointerup), and it is why the "first response" figure in each cell is measured from finger-down rather than from the action resolving.
  • Read the press-in, not the release — the release is a mockup luxury. In the real battle, confirming a command immediately swaps the command bar for the quiz card or the message line, so the buttons are gone before any release animation could play. What you will actually see in-game is the inward press, held for as long as your finger is down. Here the buttons stay put so you can tap them repeatedly, which means you also see the release. In-game, A's overshoot only shows when a tap is cancelled — finger down, then slid off. That is a fair argument for B or C: they spend nothing on a beat the player rarely sees.
  • Reduced motion. With the OS "reduce motion" setting on, A and B fall back to C's flash automatically. Nothing loses its feedback.
  • Font. The shipped UI uses bundled Zen Maru Gothic; a standalone offline file cannot load it, so this page falls back to the system face. Sizes, weights and spacing are the shipped values.
