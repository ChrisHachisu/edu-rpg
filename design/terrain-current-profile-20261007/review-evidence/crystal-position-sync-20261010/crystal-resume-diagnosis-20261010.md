# Crystal exit and resume-position diagnosis — 2026-10-10

## Finding

The first post-exit resume snapshot was not a stale SQLite/WAL read. It faithfully captured the live game's player state, but that state briefly carried the **source map ID** after the frozen scene had switched to the overworld. The evidence supports a transition-ordering window, not a persistent failure to update position after ordinary movement.

The exact Release84 frozen bundle is `derived-release84-continue/Build/Products/Release-iphonesimulator/App.app/public/assets/index-BhoGQRaA.js`, SHA-256 `ab4fc9ad1204f23b4ea55dbae2d72bdf193a52e643271bcfe8642e2210556456`. In its `WorldMapScene.performTransition` target-map branch (byte offset 4,660,706), the runtime sets destination coordinates and calls `updatePosition()` **before** `loadMap(x.targetMap)`. `updatePosition()` (offset 4,722,011) writes `{mapId: this.currentMapId, x, y, floor}`. `loadMap()` (offset 4,575,559 through `renderMap()` at 4,596,383) changes `currentMapId` but contains zero calls to `updatePosition()` and zero writes to `player.state.position`. Thus the Crystal exit can render the overworld while the saved player position still names `crystalCave` at the overworld exit coordinates.

The app's bundled recovery shell (`public/index.html`, SHA-256 `735d33eebc2bbff798262c5800bd410f83b747cf936ff2e33c18a3b8e1ee099e`) accepts any nonempty `player.state.position.mapId` in `restorable()` (lines 890–900); it does not compare that map ID to `WorldMapScene.currentMapId`. Its five-idle-tick/10-second path writes the live player state to `edu-rpg-resume` (lines 1032–1045). Scene `create` hooks do not catch this intra-scene `loadMap()` transition. This explains why the first consistent SQLite backup after the visible exit contained the cave ID: the recovery layer persisted what the game state still said, rather than a different canonical map field.

## Scope and limits

This is a read-only diagnosis. No source, bundle, app, save, or database was changed here. The minimal code-level correction, if separately authorized, would ensure a successfully loaded destination map gets a matching position write (or make recovery snapshots reject a map-ID mismatch until corrected); this report does not choose or implement either change. The evidence establishes a short-lived post-transition mismatch and its self-correction after movement, not a tested recovery regression or the behavior of every transition type.
