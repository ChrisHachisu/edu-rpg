# Elder intro on saved-town recovery — diagnosis

**Scope:** read-only inspection of the exact Release84 `App.app/public` payload, corresponding source adapter/town page, frozen game bundle, and prior town verification harnesses. No app, browser, simulator, or fixture was changed here.

## Finding

The Elder/Malachar opening is emitted by the frozen Phaser `WorldMapScene`, not by the hi-fi town iframe. In the exact shipped bundle (`assets/index-BhoGQRaA.js`, SHA-256 `ab4fc9ad1204f23b4ea55dbae2d72bdf193a52e643271bcfe8642e2210556456`), `WorldMapScene.create()` runs the five-message `intro.elder1`–`intro.elder5` sequence whenever `player.state.storyFlags['intro.done']` is false and `currentMapId === 'greenhollow'`; its completion callback sets `intro.done=true`. The matching source condition is [WorldMapScene.ts](/Users/chris/.codex/workspaces/edu-rpg-forward-20261007/src/scenes/WorldMapScene.ts:377).

The adapter’s first-entry decision is a separate, in-memory intent. [adapter.js](/Users/chris/.codex/workspaces/edu-rpg-forward-20261007/public/act1-hifi/adapter.js:934) sets it only after an actual `GameState.newGame()` call; [enterTown](/Users/chris/.codex/workspaces/edu-rpg-forward-20261007/public/act1-hifi/adapter.js:996) then passes `first=1` and consumes the intent after the iframe is ready. Missing `act1.townOpened.greenhollow` does not set that intent. [town.html](/Users/chris/.codex/workspaces/edu-rpg-forward-20261007/public/act1-hifi/town.html:427) uses `first=1` only for town spawn/facing and does not emit the Elder/Malachar story sequence; the Elder interaction is separately user-triggered.

The frozen automatic-recovery route selects the menu item whose action is `continue`, then calls `TitleScene.confirm()`. Frozen `confirmTitle()` dispatches that action to `loadGame()` and starts `WorldMapScene`; only the `new` action opens the character-creation flow, where `newGame()` is called. Recovery’s snapshot overlay preserves the whole saved `player` state. Therefore the recovery route itself does not arm the adapter’s NewGame hook. A separate `newGame()` call (for example, the explicit dev-start URL path) would be needed to do so.

The most direct explanation for the reported intro is that `intro.done` was absent/false in the actual player state loaded by recovery. The report that `townOpened` may be absent is not enough to explain it: that flag controls the hi-fi town first-entry spawn, while the intro gate reads `intro.done`. This is a code-path diagnosis; this task did not inspect or alter the reviewer’s native save fixture.

Keep `act1.townOpened.greenhollow` absent and all other fixture fields, boss flags, map/position, fresh-restart beacon, and launch flow unchanged. Do not tap New Game. Capture the recovery counter/log, whether the opening sequence appears, and the town iframe URL (`first=1` or no `first=1`).

Expected under the diagnosis: recovery still resumes the saved state; the intro sequence does not appear; `townOpened` remains absent; and no `first=1` is passed because no `newGame()` occurred. If the intro still appears, inspect the effective `intro.done` value immediately after `loadGame`/snapshot overlay and whether the explicit dev-start path or another `newGame()` call ran. Do not treat the town flag alone as a pass/fail signal for the intro.

## Bounded repair recommendation for legacy Continue

**Recommendation (not implemented here):** add an overlay-side Continue-success marker to the existing `public/act1-hifi/adapter.js` tick lifecycle; do not change the frozen bundle or merge flags from another save object. Install a one-time wrapper around `TitleScene.confirmTitle()` once the scene object exists. When the selected menu action is exactly `continue`, temporarily wrap the *current* `GameState.loadGame` function to record its boolean result, call the original `confirmTitle`, then—only if that call returned from a successful load—set only `player.state.storyFlags['intro.done'] = true` on the final live player. Restore the load wrapper only if it is still installed. This point is after Continue’s load and after any recovery wrapper has overlaid its resume snapshot, but before the queued `WorldMapScene.create()` evaluates the intro condition. Phaser `scene.start()` is queued by this app’s own cover logic (`dist/index.html`, lines 263–266), leaving this post-confirm point ahead of scene creation.

A wrapper only around `GameState.loadGame()` is insufficient for auto-recovery: recovery temporarily replaces `loadGame`, calls the original, overlays `snap.player` after that call, and only then returns. A marker set inside the underlying load can therefore be replaced by a snapshot that still lacks `intro.done`. The `confirmTitle()` wrapper can wrap whichever `loadGame` function is current at call time and mark the final live flags after the outer recovery wrapper returns. It must not set the flag for `new`, failed `continue`, or any non-Continue menu action. This preserves the New Game/New Game+ opening, since those routes call `newGame()` and never take the successful-Continue branch. It also avoids rewriting persisted save/snapshot blobs or importing unrelated flags; the existing town save naturally persists the one migration flag.

**Failable exact-path checks before accepting the repair:**

1. On the same exact Release84 candidate, use a legacy save at overworld `(69,256)` with `storyFlags: {}` and no New Game tap. Continue must load and auto-enter Greenhollow without the five-message intro; actual town entry should still be successful and use the ordinary re-entry spawn (`first=1` absent).
2. Use the real town Save action, then inspect the resulting save: it must contain `intro.done === true` and the already-earned/live flags (including `compass.visited.greenhollow`), with no unrelated flags imported from the resume snapshot. Terminate/relaunch and Continue the resulting save; the intro must remain absent.
3. Repeat from clean New Game and New Game+ paths. Each must still show the opening once, retain the adapter’s fresh-town first-entry intent/position, and set `intro.done` only after the sequence completes.
4. Make Continue fail (invalid/absent save through the supported harness path). It must not set `intro.done`, replace the player, or start WorldMapScene. Also exercise recovery with the real valid manual save plus a fresh resume snapshot missing `intro.done`; the post-overlay marker must still suppress the intro.

These checks validate the exact successful-Continue boundary, failed-load non-mutation, new-game separation, actual town Save persistence, and recovery overlay ordering. A source edit would require rebuilding the QA candidate and retesting these paths against that exact payload; this recommendation does not itself establish a pass.
