session, emulating an iPhone (390×844 @3x, `hasTouch`/`isMobile`, `Capacitor.isNativePlatform()`

**Harness:** `scripts/playthrough_census.cjs` (new, this session). Reuses the boot/save/walk
mechanics of `scripts/verify_town_owner_items.cjs`, `scripts/perf_probe.cjs`,
`scripts/browser_runtime_smoke.cjs` and `scripts/verify_dungeon_entry.cjs` verbatim, plus one

## Honesty note on the run itself

This machine was measured at **load average 260–470** and **~65–90MB free RAM** for the whole
session (`uptime`, `vm_stat`) — many other Claude sessions were running concurrently. Two
consequences, both visible below:

1. The harness's Chrome renderer was killed mid-run by the OS at least twice ("Target page,
   context or browser has been closed"). A self-healing relaunch was added so the census could
   finish, but **all of Step 2 was lost to one such kill** and is honestly UNVERIFIED, not
   PASS/DEFECT.
2. **Every raw DEFECT was individually re-examined against its screenshot before being reported
   as one here** (per the fable-mode "verify before flag" rule). Several of the harness's own
   raw DEFECT readings turned out to be test artifacts, not game bugs — detailed inline. The raw
   script output was 47 PASS / 2 UNVERIFIED / 18 DEFECT; after screenshot-by-screenshot
   verification the honest count is **43 PASS / 19 UNVERIFIED / 5 DEFECT**. The corrected number
   is what this report uses throughout.

## Defects (ranked by severity)

### 1 — BLOCKER: two independent dialogue/message boxes can stack, visually garbled, and lock movement

**Reproduction:** Fresh New Game (no save) → arrive in Greenhollow in front of the elder → the
game auto-plays its own 3-line opening narration (`intro.elder1/2/3`) via
`WorldMapScene.showMessage()` → interact with the Elder NPC (tap/Enter) while that narration is
still up. Two boxes render simultaneously: the Elder's own line ("Be safe, hero. Head east
toward the Darkfang Grotto...") stacked directly on top of the auto-narration box underneath it,
with the narration's earlier line bleeding through behind the new box. **Movement stays blocked
for the whole time both are up** — held ArrowDown for 20 real seconds produced zero movement,
because `WorldMapScene.canMove`'s gate (`!this.showingMessage && !this.isMoving`,
`src/scenes/WorldMapScene.ts:936`) sees an active message the whole time.

**Exact state:** mapId `greenhollow`, first playthrough, `storyFlags['intro.done']` still false at
the moment of interaction, hero cell front of Elder Rowan.

**Screenshots:** `05-step1-elder-dialogue.png`, `06-step1-exited-to-overworld.png` (a *second*,
independent reproduction — not caused by my script's own teleport shortcut — the movement lock
persisted for a full 20s of real keyboard input). Also reproduced in Japanese
(`63-step7-elder-dialogue-ja.png`) and in a *different* precondition — a Healer confirmation left
open when a villager dialogue opens next — in the returning-player flow
(`38-step5-greenhollow-villager-elder.png`).

**Suspected files:**
- `src/scenes/WorldMapScene.ts:377-386` — the auto-played `intro.elder1/2/3` sequence gates only
  on `!intro.done && currentMapId==='greenhollow'`, with no check for whether the town overlay's
  own dialogue is also about to open.
- `public/act1-hifi/town.html:317-318` (`promptEl`/`dialogueEl` `pointerdown` → `interact()`) and
  `:480` (`interact()`) — the town's own tap-to-interact never checks the parent's
  `showingMessage` state before opening its own box.
- `public/act1-hifi/adapter.js:495-520` (`currentChrome()` / the `dialogue` flag forwarded to the
  town) — this only hides the town's **pad/prompt controls** while the parent's message is up
  (per the existing "ITEM 7" fix); it does not prevent the town's own dialogue box from opening on
  top of it.

**Note:** the two reproductions have different exact preconditions (one is the auto-intro racing a
tap, the other is my census's `&at=` teleport not dismissing a prior Healer message before
triggering the next NPC) but both land on the same underlying gap: nothing in this stack enforces
"only one dialogue surface visible at a time" between the parent's `showMessage()` system and the
town iframe's own dialogue box. Given the target audience is grade-schoolers tapping eagerly, the
auto-intro race (reproduction 1) is very plausible in real play and is rated blocker because it can
strand a brand-new player, unable to move, on their very first screen.

### 2 — MAJOR: possible wall-clip in Sunken Cellar B1F, blocking the route to the stairs

**Reproduction:** Enter Sunken Cellar, walk toward the mapped `stairsDown` cell (local (8,6) per
`public/act1-dungeon-floors.json`). Following the shortest open-cell path from the mouth, the hero
stops dead at local cell (13,18) pushing ArrowUp and does not move again.

**Exact state:** mapId `sunkenCellar`, floor 1, cell (13,18), facing up.

**Screenshot:** `20-step4-sunkenCellar-floor2-or-stuck.png` — the hero is visibly wedged against
the base of a large boulder/rock-formation decoration; this was **not** a random-encounter
interruption (compare the mistyGrotto case, where the screenshot clearly shows a battle instead —
this one clearly shows the dungeon floor, label "Sunken Cellar B1F" visible, no battle UI).

**Suspected mechanism:** dungeon collision is enforced by `A1D_BLOCK` against `scene.mapData`
(`public/dq-tiles.js:2888-2920`), which is a *baked/runtime* representation, separate from the
*authored* floor layout in `public/act1-dungeon-floors.json` (the `rows` grid this census's BFS
pathfinder used, on the stated assumption that `'#'` is the only blocked character). If the
boulder decoration's collision footprint at runtime is wider than what the authored rows claim is
open, a player following the natural route to the stairs would hit the same wall a real controller
would. **Caveat:** this was observed once, via an automated path, not confirmed with a human/manual
walk-around; recommend a manual sim/device check of Sunken Cellar B1F before treating this as
certain.

### 3 — MAJOR: New Game after a Continue skips the overwrite-confirmation

**Reproduction:** Save in a town (Step 6) → reload the page → Continue (confirmed working,
restores state exactly) → open the field menu Settings tab → "title screen" (quit) → New Game.

**Expected:** `TitleScene.confirmTitle()` checks `SaveManager.hasSave(activeProfileId)` and, if
true, calls `showOverwriteConfirm()` (`src/scenes/TitleScene.ts:771-793`) before ever reaching
character creation.

**Observed:** tapping New Game went **directly** to the "Create Your Hero" screen — no overwrite
warning shown at all (`ts.mode` was already `'create'`, not `'overwrite'`, the instant after the
tap).

**Screenshot:** `58-step6-newgame-overwrite-confirm.png` (filename is aspirational; it is actually
the character-creation screen, not a confirm dialog).

**Risk:** a player who just Continued a save, then decides to start over, gets no "this will erase
your progress" warning at all before their save is overwritten on Start Game.

**Suspected file:** `src/scenes/TitleScene.ts:771-793` (`confirmTitle()`), and/or whatever code
path `routeTitle` in `public/ui-overhaul.js` takes when re-entering the title from the in-field
"quit to title" action rather than a fresh page load — worth checking whether
`SaveManager.getActiveProfileId()`/`hasSave()` gets a stale answer specifically after a
scene-internal `ms.scene.start('TitleScene')` (as opposed to a full reload).

### 4 — MAJOR (needs re-verification): Port Sapphire overworld→town transition did not fire

**Reproduction:** Seed one cell outside Port Sapphire's overworld door (`(133,347)`, per
`LANDMARKS` in `public/act1-world-map.js`), walk ArrowDown (the correct direction — `exit.y < at.y`
for this landmark) for 14s.

**Observed:** hero remained on `overworld` at `(133,349)` (the landmark's own trigger cell,
i.e., she visibly walked all the way to the door) with the town overlay never appearing
(`{"ready":"false","townId":null}`).

**Screenshot:** `49-step5-portSapphire-entry.png` — hero is standing directly in front of the
miniature Port Sapphire icon on the overworld.

**Caveat:** Greenhollow and Millbrook used the **identical** mechanism in the same run and
succeeded, which argues for a real, town-specific issue — but this was the same stretch of the run
where host load was measured at 260–470 and Chrome had already been killed twice by the OS.
**Recommend re-running this one entry under normal host load before treating it as confirmed** —
if it reproduces cleanly, `public/act1-world-map.js`'s `portSapphire` landmark entry and its
`toX`/`toY` wiring into the overworld transition are the place to start.

### 5 — MINOR: Millbrook shop counter interaction did not open ShopScene

**Reproduction:** Teleport (`&at=`) to Millbrook's `shopCounter` cell `[15, 38.69]`
(`public/act1-hifi/town/millbrook-town.json`), call `interact()`.

**Observed:** `ShopScene` never became active (`open=false`).

**Screenshot:** `42-step5-millbrook-shop-open.png` — the hero is standing near the mill/haystacks,
visibly **away** from the market-stall awning visible at the bottom of the frame, suggesting the
`&at=` placement (or the walkable-authority snap it goes through) did not land her within
`nearestService()`'s 1.2-cell tolerance box (`public/act1-hifi/town.html:421-427`) of the counter.
Greenhollow's identical mechanism, with its own `shopCounter` coordinate, worked correctly in the
same run (`30-step5-greenhollow-shop-open.png`), which points at Millbrook's specific
`shopCounter` value rather than the general mechanism.
