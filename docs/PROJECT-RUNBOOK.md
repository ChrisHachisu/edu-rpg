## 1. ⚠️ VERIFICATION DISCIPLINE — verify the RENDER, never the source

The deployed game is a **hand-patched bundle + runtime re-skins** (see §3), so "the code looks right"
is **never** proof — `dq-tiles.js` repaints tiles and `hero-override.js` swaps textures at runtime, and
the committed `src/` is NOT what ships. Every UI/gameplay change MUST be confirmed against the actual
rendered result.

**Drive the render yourself** (you have the tooling — §6): build → install on the canonical iPhone 17
sim → drive with `idb ui tap|swipe|text` → `xcrun simctl io … screenshot` → read the pixels; and/or run
the headless `.eduharness/` Playwright harness against a static dist serve. This is exactly how TF
build 5 was verified.

**Rules:**
- Never claim a visual/gameplay change "works" from source review alone; if for any reason a render is
  left unverified, say so explicitly and mark it **UNVERIFIED**.
- A single screenshot can't prove a scroll/drag/animation fired — record a short
  `xcrun simctl io <UDID> recordVideo out.mp4` and check the frames for motion (this bit us more than once).
- You can run **multiple simulators at once** (`xcrun simctl boot <UDID>` per device; each needs its own
  `idb_companion` on its own port to drive independently) — useful for parallel device/regression checks.

## 2. ⚠️ NON-NEGOTIABLE DON'Ts (each one caused real damage before)

1. **NEVER `npm run build` / `npx vite build` and deploy.** The deployed game's TypeScript source was
   *never committed* — `main` is an old 120×160 regressed world. A fresh build emits a **2.44 MB /
   72-monster** bundle that **silently drops V3 content**; the correct shipped bundle is **~4.99 MB /
   75 monsters**. Always `wc -c dist/assets/index-*.js` before shipping — ~2.4 MB means someone
   rebuilt from source and destroyed content.
2. **NEVER use `npm run dev` / `npx vite` / any live-preview server on the source tree.** It serves the
   regressed `main` source, not the real game. View the game ONLY via the live site or a static serve
   of the pre-built bundle (`npx serve -s dist -l 5174`).
3. **NEVER edit the bundle in place with a script that reads+writes the same file.** Past scripts
   corrupted `index-BhoGQRaA.js` to **6 GB and 10 GB**. Bundle edits: read → modify in memory → write
   to a NEW `/tmp/vX.Y.Z-build.js` → assert size 4.5-5.5 MB → `wc -c` → only then copy to dist. Never
   run the same edit script twice (a stray background copy duplicates content).
4. **NEVER add/remove a `h()` (seeded-random) call in dungeon generation.** It reshuffles the entire
   dungeon layout and has repeatedly produced "all walls" bugs. Consume-but-ignore (`(h(), true)`)
   instead of removing.
5. **NEVER `git checkout <commit> -- .` on gh-pages, and never `git add -A` on gh-pages with
   `.eduharness/`/`backups/` present.** Both have deleted the monster sprite PNGs / shipped a wrong
   bundle. Deploy via an isolated `/tmp` git worktree; only ever replace the JS bundle file, never
   touch `assets/monsters/`. Verify monster PNG count stays ≥71 before AND after any gh-pages op.
6. **NEVER re-introduce a custom font file.** The smooth system font is intentional (a pixel font
   loaded fine on gh-pages but failed silently on localhost). Font is set in `src/utils/constants.ts`
   → `FONT_FAMILY` only.
7. **NEVER modify Crystal Cave generation** (design-locked as "sacred").

## 3. Architecture — how the game is actually built (READ THIS)

The game you see is **NOT** the committed `src/` TypeScript. It is:

- **A pre-built Phaser bundle** at `dist/assets/index-BhoGQRaA.js` (~4.99 MB, beautified/multi-line —
  grep it, don't read whole). This is the compiled game (75 monsters, SAVE_VERSION 4, 320×400
  overworld with portals). Its source was never committed → **a dispatched code-review of the game is
  impossible; render verification is the only gate.**
- **Additive override layers** loaded AFTER the bundle by `dist/index.html`, each re-skinning or
  re-behaving the game at runtime without recompiling:
  | file | what it does | source of truth |
  |---|---|---|
  | `dist/ui-overhaul.{js,css}` | "Storybook Quest" DOM UI overlay (menu/shop/healer/intro/battle/title) — a full-screen DOM layer over Phaser | `edu-rpg/public/ui-overhaul.*` |
  | `dist/hero-override.js` | swaps the hero texture to the locked v17 walk sheet (A/B variant), hides the touch control-hint, defaults locale to device | `edu-rpg/public/hero-override.js` |
  | `dist/dq-tiles.js` + `dist/owprops/` + `dist/props/` | DQ terrain re-skin (overworld/town/dungeon), repaints tiles at runtime | `edu-rpg/design/dq-world-art/dq-tiles.js` |
  | `dist/assets/hero/hero-*-walk.png` | v17 hero sprite sheets (openface / feminine) | codex output (see §8) |
  | `dist/assets/monsters/*.png` | 75 monster sprites (RGB, black bg, chroma-keyed at runtime) | `monster-sprites/received/V2/` |
- **The repo-root `edu-rpg/index.html`** — the Capacitor entry; declares the viewport, the touch d-pad
  + field-tabs, and loads the bundle + overrides. `dist/index.html` is its built twin (relative asset
  paths). **`dist/index.html` is what actually ships** (Capacitor `webDir: dist`).

**The load-bearing consequence:** to change gameplay/UI, you almost always edit an **override file**
(`public/*` or `dq-tiles.js`) additively — you rarely touch the bundle, and when you must, follow the
bundle-patch protocol (§2.3). **Verify the RENDER** (dq-tiles/hero-override repaint at runtime), never
the source.

### The DOM UI overlay (`ui-overhaul.js`) — the trickiest subsystem

It replaces Phaser scene UI with a DOM layer (`#qok-ui`, z-200) that polls `setInterval(50ms)`, detects
the active Phaser scene, and renders that screen's DOM from live state (`window.__GAME_STATE__`,
`window.__QOK`, `window.__PHASER_GAME__`). **Bridge pattern (critical):** the overlay hides the Phaser
canvas and drives the real logic by calling the existing scene methods. **Taps are pointer-routed**
(capture-phase `pointerGuard` on `document`, routes on `pointerup`, `stopPropagation`s taps away from
the still-live Phaser input; the name `<input>` passes through natively with a bubble-phase shield).
**This is fragile on iOS — see the #1 gotcha in §9.**

## 4. How to make a change + ship it

**Additive override change (the common case):**
```bash
# 1. edit the source-of-truth file, e.g. edu-rpg/public/ui-overhaul.js
# 2. copy it into dist (what ships)
cp public/ui-overhaul.js dist/ui-overhaul.js        # keep public↔dist in SYNC (both directions must match)
# 3. sync dist into the iOS project (Capacitor)
npx cap copy ios
# 4. VERIFY THE RENDER (orchestrator/owner — you can't). Then ship (§5).
```
Always keep `public/*` and `dist/*` identical for the override files — a future `public→dist` copy will
otherwise silently revert your fix. (This bit us: edit dist, forget to sync public.)

**Bundle change (rare, high-risk):** follow §2.3 (new temp file + size assert) and log it; a Claude
code-review agent can't see bundle patches, so render/harness verification is the ONLY gate.

## 9. GOTCHAS ledger — friction that bit us before

1. **iOS touch: the DOM overlay must SWALLOW pointer/touch, not just handle `click`.** The still-live
   Phaser scenes under the overlay keep their pointer+keyboard handlers; on WKWebView a tap reaches
   Phaser FIRST and iOS often fires **no `click`**. This was TF-build-4's whole create-screen failure
   (a variant tap toggled the language, the name box couldn't focus). Fixed by the pointer router in
   `ui-overhaul.js` (§3). **Rule:** any DOM overlay replacing a live Phaser/canvas scene must
   `stopPropagation` pointer events at capture and route on `pointerup`. Do NOT revert to a click-only
   handler.
2. **Any Phaser affordance under the opaque overlay must be re-bridged to the DOM.** Tap-to-advance,
   Game Over, damage/victory feedback, the overworld `showMessage` dialogue — all invisible/dead under
   the overlay unless bridged. The overworld dialogue is advanced by a DOM tap-catcher
   (`syncMsgCatcher` → `wm.advanceDialog()` when `wm.showingMessage`; the method's 300ms debounce
   prevents double-advance) because the d-pad/field-tabs overlap the message box.
3. **Fuzzy Phaser HUD (bug 4, OPEN).** `Scale.RESIZE` sizes the canvas backing store to CSS px
   (measured 402×812 at DPR 3) → the Phaser layer renders at ~⅓ device resolution → soft HUD/dialogue
   text. DOM-overlay screens (menu/battle/shop) are crisp; only the Phaser overworld HUD is soft.
   Phaser 3.5+ removed `resolution`; a DPR-aware fix needs a full ScaleManager/renderer adaptation — a
   naive `canvas.width` + `renderer.resize` breaks camera/HUD/**input** coordinates. **Owner wants this
   as a dedicated, carefully-verified effort — do NOT hand-patch it into the bundle rashly.**
4. **`IS_TOUCH` feature-detect is unreliable in the WKWebView shell.** `hideGuideOnTouch` worked in the
   sim but the owner saw the guide on-device → also treat `window.Capacitor` native as touch.
5. **`quizStats.byCategory` must be defaulted `{}` on every save load/copy** — a save lacking it throws
   in `recordAnswer` and silently freezes the battle turn cycle (the overlay swallows the throw).
6. **`pathBetween()` is 3 tiles wide** — it also writes `(px+1,py)` and `(px,py+1)`; a path routed
   within 2 tiles of a barrier silently punches through it. Barrier integrity is non-negotiable; the
   final seal pass at `y=101` is the last line of defense.
7. **Deployed dungeon dims are 100×100** (not older per-dungeon table values). Verify a floor's
   playability by spawn walkability, not raw wallPct. Don't force-load a dungeon from the console
   (`loadMap`) — seeded gen skips setup and shows a bogus all-wall grid even on a correct build.
8. **`expo prebuild`/`pod install` don't apply here** (Capacitor, not RN/Expo) — ignore chalkmap-v2's
   Hermes / EAS-env / prod-DB ship guards; they're RN-specific and not in this game's Fastfile.
9. **In-app preview shows the WRONG version** — never trust `preview_start`/vite; verify via the live
   site, a static dist serve, or the sim.
